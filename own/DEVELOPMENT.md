# macOS 开发版构建与安装

## 日常开发与正式发布

默认顺序为：修改源码 → 在 Mac 构建并安装开发版 → 自动验证和实际功能测试 → 用户确认并授权发布 → Windows 自动构建与基础检查 → 发布 npm → Windows 安装后抽查。peter-new 人工测试按需安排。

正式发布目标为 `win32-x64`，包括 Windows 桌面和配套 Node/npm/Python 运行时。Mac 只维护本机开发版；历史 Mac 制品保留。CI 构建、清单合并、验收证明、npm 内容块及发布前打包检查使用一致的 Windows 目标，历史双平台绑定仍按其原始平台集合验证。Mac 开发运行时使用 `own/runtime/mac-development.json` 中保留的独立来源，不依赖后续 Windows 正式包包含 Mac 资源。

每次修改后执行下方的开发构建入口。以本次 `result.json`、`source-inventory.json` 和已安装应用的 `own-development.json` 为验收依据，记录本次功能测试结果。新的产品源码先加入 Git 索引，以进入构建清单。代码变化后重新构建测试，确保正式发布的功能与开发版验收一致。

开发版配置、凭据及对话保留在独立目录，替换应用前创建恢复备份。正式版与原版 Codex 保持各自的安装和数据，只有用户明确要求时才更新正式版。

用户确认测试通过并要求发布后，在自有 Windows 电脑完成构建和检查，再通过 npm-release-kit 的 local 模式发布，发布后核对准确版本与渠道。日常更新通过 npm；完整离线安装包和 NAS 交付仅在用户明确要求时手动执行。GitHub Actions/OIDC 为用户明确选择的独立路线，仓库云端任务保留显式调度入口。

## 构建入口

源码入口是仓库根目录；正式版与开发版共用 `own/` 的实现。
开发版专用脚本负责本地构建、验证、备份和安装，底层继续使用 `own/build.mjs`。

在仓库根目录运行：

```sh
node own/dev.mjs --install --launch
```

仅构建和验证时运行 `node own/dev.mjs`，查看参数运行 `node own/dev.mjs --help`。
评估指定官方稳定版 CLI 时，运行 `node own/dev.mjs --cli-version 0.167.1 --install --launch`。
该选项从官方 npm 包下载固定版本，校验 SHA-512 完整性、包身份、布局与实际版本，保留完整配套资源，并将来源与摘要写入本次构建记录。此覆盖入口仅用于本地 Mac 开发版。
开发版应用尚未安装时，入口先验证候选、备份已有开发版数据，再进行首次安装；验证失败的候选保留在报告目录。
单独评估 CLI 与现有桌面外壳的兼容性时，追加 `--upstream-app /Applications/ChatGPT.app` 明确选择本机官方输入。入口验证 OpenAI 官方签名，并分别记录所选外壳版本、CLI 版本及其与当前官方桌面版本的关系。
安装命令应从开发版以外的终端或 Agent 执行。脚本仅支持 macOS ARM64，要求已安装仓库依赖、独立 Node 22+ 和已配置可信的开发签名身份。

脚本冻结当前提交及工作区已跟踪文件，另收录本入口、开发说明和入口测试。其他未跟踪文件需先加入 Git 索引，才成为构建输入。冻结时发现文件变化会停止；冻结后的修改留给下一次构建。源码清单与摘要保存在报告目录，依赖使用本机已安装版本。

每次构建使用全新 `out/dev-build-*.noindex` 目录，记录提交、源码摘要、签名指纹、实际 Node 版本和各阶段日志。先查询当前官方 Mac 版本；本机原版 App 的版本、构建号和官方签名全部通过校验时，直接复用其只读程序输入，否则同步下载官方输入。两条路径随后都完整应用当前上游适配与产品源码，并验证包签名、隔离后台握手、离线模型协议、真实工具与补丁调用、中断后恢复，以及真实桌面工作台和输入框。验证使用隔离测试配置和本地模拟服务。

全部验证通过后，安装流程正常退出开发版，等待其主进程与后台退出，备份开发版数据，再替换固定位置 `/Applications/codex-own 开发版.app`。备份保留文件权限、时间及符号链接，临时通信 socket 单独记录并跳过。旧 App 保存在本次报告目录的 `previous-development.bundle`；安装签名校验失败会恢复旧 App，失败候选另存。安装后启动失败会记录错误并保留备份，供检查。

开发版继续使用 `~/.codex-own-dev/Library/Application Support/codex-own-independent`，固定 Bundle ID 为 `local.codex-own.development`。配置、认证与对话保持原位，npm 自动更新处于关闭状态。

结果入口为本次目录中的 `result.json`，其中包含旧 App 和数据备份路径。签名证书与密钥由既有本机开发签名配置管理。脚本不执行发布；正式版发布由仓库本地发布入口管理。

## 构建副本自动保留

开发入口在构建前及写入本轮结果后执行本地清理。默认保留当前已安装源码指纹对应的完整恢复构建，以及最近一套成功恢复构建；每套保留源码工作副本、旧应用和配套数据备份。主工作区与 `out/<操作>/repo/out` 中的隔离构建一起核对。每轮的结果、源码清单、日志及 GUI 验收证据长期保留。

旧源码实际改动先保存为拥有仓库内的 `refs/own-recovery/…` Git 恢复引用；旧数据备份中当前数据和保留备份未覆盖的文件先生成私有压缩归档，并解包核对内容、链接和权限。保留备份的 SQLite 数据库连同 WAL 在隔离副本中验证，恢复应用通过签名检查后才淘汰旧完整目录。清理清单、归档位置及释放空间记录在 `out/development-retention-*/`。独有历史数据的紧凑归档作为恢复资料保存。

独立预览：`node own/dev.mjs cleanup plan`。执行已授权的清理：`node own/dev.mjs cleanup run --yes`。构建锁、活动进程引用、来源不明、恢复证据缺失或校验失败会保留文件并给出原因；清理失败不回滚已成功的安装。未被成功构建替代的失败现场保留七天。需要额外保留的构建可写入 `retention-pin.json`，包含 `reason` 和 ISO 时间格式的 `reviewAfter`；到期后由执行者复核解除。

已完成归档校验但删除中断时，使用 `node own/dev.mjs cleanup resume <原清理目录> --yes`。入口复用原清单，重新核验应用指纹、构建记录、目录身份、Git 恢复引用、数据归档摘要和保留备份后继续；目录暂时繁忙或非空会执行有界重试。已完成的操作拒绝重复恢复。

本机清理属于仓库开发工具能力，不改动 npm 更新缓存、正式安装或固定运行时来源。变更验证使用临时夹具覆盖真实归档、恢复读取和拒绝删除路径，并通过本机清理入口实测；桌面功能变化仍执行前述开发版构建验收流程。

## Tuda 独立软件边界

Tuda 与 codex-own 分别安装、版本管理和发布。codex-own 仅打包经过摘要和能力合同核验的 Tuda board-only 插件/CLI/MCP 连接组件；通过已运行的独立 Tuda 本地协议连接，宿主退出保留 Tuda。开发入口验证连接包，打包检查拒绝 Tuda 桌面树。独立软件与插件更新分别处理；真实桌面版本、协议和授权隔离核对通过后再交接员工身份。Dev 联调复用现有实例与明确 userDataPath。当前合同、生产端缺口及验收边界见 `own/TUDA-INTEGRATION-HANDOFF.md`（从 own 目录访问时为 `TUDA-INTEGRATION-HANDOFF.md`）。

## 执行阶段与耗时诊断

聊天运行时显示当前阶段、本阶段耗时和本轮耗时：请求准备、访问权限校验、等待模型首个响应、等待流内容、模型推理、回复输出、工具执行、等待用户操作。状态来自模型流和 App Server 事件；收到响应头不代表已收到正文。工具执行状态只表示工具尚未返回，不推断服务内部进度。完成、失败、中断和后台断开后停止计时；不同对话分别关联。

私有数据根目录的 `core/execution-timing/` 保存 JSONL 元数据日志。通过 threadId、turnId、requestId 关联提交、请求体接收与准备、鉴权完成、向上游发出、响应头、首个响应字节、推理/正文/工具参数、请求结束，以及运行时收到内容和工具起止。请求内耗时使用单调时钟；跨进程关联使用系统时间。响应头等待包含网络和服务端处理，尚不能单凭该值区分网络传输与服务端排队。

日志不保存请求正文、响应正文、命令、URL、HTTP 头或凭据。每份日志约 4 MiB 轮换，最多保留八份；日志失败不阻断执行。此诊断不改变模型、推理强度或请求中的业务内容。


## 自有 Windows 本地发布

在干净、已提交的源码检出中运行 `node own/ci/local-native-build.mjs 版本 全新证据目录`。入口执行源码测试、固定官方输入构建、模型与补丁协议、历史恢复、桌面和原生设备服务、规范归档及真实安装更新检查。local-proof.json 记录 execution=local、源码提交与输入指纹、检查日志摘要和制品摘要，不包含账号配置。

在发布电脑组合已验证的 Windows 制品和未变化的固定工具运行时，运行 `node own/ci/publish-npm-assets.mjs 制品目录 --local --proof 本地回执` 发布缺少的内容块。内容块使用 npm-release-kit 的固定待发布包，稳定候选目录与私有回执跨认证重试保留。账户验证在普通 Google Chrome 完成。规范归档和 registry 内容复核通过后，绑定本地回执，通过 npm-release-kit prepare/publish 的 local 模式发布主包，并校验精确版本、integrity、dist-tag 及本机 Codex 配套 Skill。

新本地记录的 execution 和 recipe 标明实际执行器；兼容字段 workflow 引用历史发布配方，run 是本地回执编号。既有云端构建与运行时的来源记录继续保留，核验时按真实执行方式分别处理。
